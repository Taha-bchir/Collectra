\chapter*{Abstract}
\phantomsection
\addcontentsline{toc}{chapter}{Abstract}

This report describes the final-year internship project completed at
\textbf{PeakSoft GmbH} (Wuppertal, Germany).
The project is called \textbf{Collectra} -- a web platform for managing debt
collection and customer reminder campaigns.

Debt collection teams often use separate tools: spreadsheets to store data, email
threads to track communication, and general CRM systems that cannot track debt
lifecycles.
Collectra solves these problems by bringing debt records, campaigns, team actions,
and customer communication into one secure, workspace-based SaaS environment.

The platform includes: JWT-based login with HTTP-only session cookies, strict
workspace-level data separation, role-based access control for managers and agents,
a full debt lifecycle from import to payment, time-limited secure customer links,
Stripe payment confirmation with duplicate-prevention logic, automatic invoice
creation and delivery via Brevo, campaign email tracking, and a manager dashboard.

The project followed the Scrum agile method across four two-week sprints.
Tasks were tracked in Linear.
The application runs on \textbf{Vercel} at the domain \texttt{collectra.xyz},
using a GitHub CI/CD pipeline where changes are merged from the \texttt{develop}
branch into \texttt{production} and published automatically.
The technical stack uses Next.js, React, TypeScript, Hono, PostgreSQL (Supabase),
and Prisma ORM, organized in a Turborepo monorepo.

\medskip
\noindent\textbf{Keywords:}
debt collection, SaaS, campaign management, JWT, Scrum, Next.js, TypeScript,
PostgreSQL, Prisma, Supabase, Stripe, invoice generation, Vercel, CI/CD,
email tracking.

\chapter*{General Introduction}
\phantomsection
\addcontentsline{toc}{chapter}{General Introduction}
% =============================================================================

Debt collection is an important process for banks, telecom companies, and service
providers that manage many unpaid invoices.
Despite its importance, most collection teams still use separate tools: spreadsheets
for data, email threads for communication history, and CRM systems that were not
built for debt lifecycle tracking.
The results are easy to predict: poor traceability, weak team collaboration, and no
single view of campaign progress.

The \textbf{Collectra} project was built during this internship at PeakSoft GmbH
to fix these problems.
Collectra is a SaaS web platform that brings debt data, campaigns, team activity,
and customer communication into one secure, workspace-based environment.
It replaces scattered tools with one role-aware application that covers the full
debt lifecycle, from the first import to payment confirmation and invoice delivery.

From a technical side, Collectra is built on a modern TypeScript monorepo.
The frontend uses Next.js and React.
The backend uses Hono with a validated OpenAPI contract and Zod schemas.
The database is managed with Prisma ORM on PostgreSQL via Supabase.
Development was organized using the Scrum agile framework, tracked in Linear, over
four two-week sprints.
The platform is deployed on Vercel at \texttt{collectra.xyz} through an automated
GitHub CI/CD pipeline.

This report is organized as follows:

  \item \textbf{Chapter 6 -- Sprint 4: Payment, Invoicing, and Analytics:}

\end{itemize}

\section{Project Context}

\subsection{Main Issue}

Debt collection teams face repeated operational problems.
Follow-up work is spread across many tools: debt data is stored in spreadsheets,
contact history is tracked in email threads, and reminder statuses are updated
manually.
This makes it hard to audit past actions, share information between team members,
or monitor campaign progress in real time.

The specific problems identified at the start of the project were:
\begin{itemize}
  \item debt data is scattered with no single source of truth;
  \item reminders, promises, and payments are hard to trace;
  \item agents and managers cannot collaborate easily;
  \item there is no single view of campaign progress or debt status;
  \item there is no secure way for customers to check their own debt information.
\end{itemize}

The main question is therefore: \emph{how can we build a secure, scalable platform
that brings all debt collection work together while keeping each workspace's data
completely separate?}

\subsection{Analysis of Existing Solutions}

A review of available tools showed the following limits:
\begin{itemize}
  \item \textbf{Spreadsheets (Excel, Google Sheets):} flexible but hard to audit,
        with no role control, no lifecycle tracking, and no secure customer access;
  \item \textbf{Generic CRM tools (Salesforce, HubSpot):} built for sales pipelines,
        not debt status tracking; often too complex or too expensive for small
        collection teams;
  \item \textbf{Manual link sharing (email attachments):} no expiry control, no
        authentication, and no audit trail.
\end{itemize}

\subsection{Overview of the Proposed Solution}

The proposed solution is \textbf{Collectra}, a workspace-based SaaS platform that
covers all five key capabilities that existing tools only address partly,
as shown in Table~\ref{tab:comparison}.

Collectra offers:
\begin{itemize}
  \item secure login and role-based access control;
  \item workspace-level data separation for multi-team use;
  \item campaign creation and bulk CSV debt import;
  \item a full debt lifecycle (Imported $\to$ Notified $\to$ Promised $\to$ Paid);
  \item JWT-secured personal customer links with a 30-day expiry;
  \item an operational dashboard for managers.
\end{itemize}

\section{Collectra Platform Requirements}

\subsection{Identification of the Actors}

The Collectra platform has four main actors:
\begin{itemize}
  \item \textbf{Owner / Manager:} responsible for workspace setup, team invitations,
        campaign supervision, and dashboard monitoring;
  \item \textbf{Agent:} handles daily debt follow-up, records actions and promises,
        and creates customer personal links; agents can also create new workspaces
        and are assigned the Owner role for any workspace they create;
  \item \textbf{Customer:} views personal debt information through a secure,
        time-limited link without needing an account;
  \item \textbf{System services:} the Supabase authentication provider and the
        email notification service (Brevo).
\end{itemize}

\subsection{Role Responsibilities}

This subsection summarizes the practical differences between the three human
roles used throughout this report: \textbf{Manager}, \textbf{Agent}, and
\textbf{Customer}. Use these definitions when writing user stories and when
defining access controls in the API.

\begin{table}[H]
  \centering
  \renewcommand{\arraystretch}{1.2}
  \begin{tabular}{|p{2.8cm}|p{8.2cm}|}
    \hline
    \textbf{Role} & \textbf{Key Responsibilities and Permissions} \\
    \hline
    Manager & Workspace administrator: creates and configures workspaces, invites members, assigns roles, reviews campaign performance on the manager dashboard, and performs Manager-only actions such as changing workspace-level settings and deleting campaigns. Managers have full workspace privileges. \\
    \hline
    Agent & Day-to-day operator: creates campaigns (CSV upload), imports debts, reviews and updates debt records, records actions and payment promises, and initiates customer outreach. Agents can perform all operational tasks but cannot perform Manager-only administrative operations. \\
    \hline
    Customer & External recipient: does not have an account. Receives transactional emails containing a time-limited JWT link that allows viewing debt details (amount, due date, campaign) and triggers audit events (email open, link click). Customer actions are recorded for manager analytics. \\
    \hline
  \end{tabular}
  \caption{Role responsibilities and permissions}
  \label{tab:roles}
\end{table}

The system enforces these differences via the role-guard middleware: Manager-only
endpoints return \texttt{403 Forbidden} for Agents, and public customer access is
provided exclusively via signed, time-limited JWT links without requiring an
account.


\subsection{Functional Requirements}

\begin{itemize}
  \item Secure user login and session management;
  \item Workspace creation and strict workspace-level data separation;
  \item Team invitation and role assignment;
  \item Campaign creation, setup, and lifecycle management;
  \item Bulk CSV import for debt records;
  \item Debt status tracking across a defined lifecycle;
  \item Creation and management of JWT-secured customer personal links (30-day
        expiry by default);
  \item Customer debt viewing via personal link (no account needed);
  \item Stripe payment confirmation with duplicate-prevention logic;
  \item Invoice creation and delivery after confirmed payment;
  \item Dashboard KPIs for campaign and debt monitoring;
  \item Action history log for full traceability;
  \item Campaign-level email tracking analytics.
\end{itemize}

\subsection{Non-Functional Requirements}

\begin{itemize}
  \item \textbf{Security:} JWT tokens signed with HMAC-SHA256, HTTP-only cookies,
        and middleware checks for every protected endpoint;
  \item \textbf{Maintainability:} modular monorepo architecture with shared packages
        and a single Prisma schema as the source of truth;
  \item \textbf{Performance:} efficient handling of bulk CSV imports with Prisma
        transaction batching to avoid database timeouts;
  \item \textbf{Reliability:} validated API contracts via Zod, database-level
        constraints, and idempotent payment confirmation logic;
  \item \textbf{Usability:} clear dashboard workflow with a small learning curve,
        confirmed through iterative stakeholder feedback during each sprint review.
\end{itemize}

\section{General Architecture of the Application}

Collectra is structured as a \textbf{monorepo} managed with pnpm and Turborepo.
It has four main packages:
\begin{itemize}
  \item \texttt{apps/web} -- the Next.js frontend application;
  \item \texttt{apps/api} -- the Hono backend REST API;
  \item \texttt{packages/db} -- the shared Prisma client and database schema;
  \item \texttt{packages/types} -- shared TypeScript types and Zod validation
        schemas.
\end{itemize}

The logical architecture separates four main areas: authentication and session
management, workspace and team management, campaign and debt management, and customer
access.
Each area maps to a set of API routes and frontend pages.
All communication between areas uses typed Zod-validated contracts, so the API
surface is consistent and both frontend and backend always share the same type
definitions.

\section{Deployment and CI/CD Pipeline}
\label{sec:deployment}

\subsection{Hosting Infrastructure}

Collectra runs on \textbf{Vercel}, a cloud platform built for Next.js applications,
under the custom domain \texttt{collectra.xyz}.
The PostgreSQL database is managed by Supabase on their cloud infrastructure.
All environment variables (database connection strings, JWT secrets, Stripe keys,
Brevo API key) are set as Vercel project environment variables and are never stored
in the repository.

\subsection{Git Branching Strategy}

The project uses a two-branch Git workflow on GitHub:

\begin{itemize}
  \item \textbf{\texttt{develop}:} the active development branch where all feature
        branches are merged after code review. This branch holds the latest
        integrated work in progress.
  \item \textbf{\texttt{production}:} the stable branch that drives live
        deployments. A pull request from \texttt{develop} into \texttt{production}
        is opened at the end of each sprint after all tests pass.
\end{itemize}

\subsection{Automated Deployment Pipeline}

Vercel is connected directly to the GitHub repository.
Every merge into the \texttt{production} branch triggers an automatic Vercel build
and deployment:

\begin{enumerate}
  \item Developer pushes feature work to a feature branch and opens a pull request
        into \texttt{develop}.
  \item After review, the feature branch is merged into \texttt{develop}.
  \item At sprint end, \texttt{develop} is merged into \texttt{production} via a
        pull request.
  \item Vercel detects the push to \texttt{production}, runs the Turborepo build
        pipeline, and publishes the updated application to \texttt{collectra.xyz}.
  \item Vercel also creates a unique preview URL for every pull request, so
        stakeholders can review changes before they go live.
\end{enumerate}

This pipeline makes sure the live environment always reflects a tested and reviewed
state, and that every deployment can be traced to a specific Git commit.

\subsection{Sprint 1 Business Logic}

\subsubsection{Authentication}

Authentication is handled by Supabase Auth using email and password.
When login succeeds, the backend sets an HTTP-only session cookie that contains the
user's JWT.
A Next.js middleware layer checks this cookie on every protected route and page, and
redirects unauthenticated requests to the login screen.
This approach stops token theft via JavaScript and protects all workspace data
behind a single, centrally managed guard.

\subsubsection{Workspace Isolation}

Every API endpoint that accesses workspace resources checks a
\texttt{workspaceId} guard before processing any data.
The system confirms that the logged-in user is an active member of the requested
workspace, so data from one workspace is never visible to users of another.

\subsubsection{Invitation Flow}

When a manager invites a user, the system:
\begin{enumerate}
  \item creates a unique, time-limited invitation token;
  \item saves the invitation record with status \textit{Pending} in the database;
  \item sends an email with a signed acceptance link;
  \item on acceptance, creates the workspace membership with the assigned role
        and marks the invitation as \textit{Accepted}.
\end{enumerate}

\subsection{Sprint 2 Business Logic}

\subsubsection{Debt Lifecycle in Sprint 2}

In Sprint 2, the debt lifecycle begins with two states:

\begin{center}
  \texttt{Imported} $\;\to\;$ \texttt{Notified}
\end{center}

When a campaign CSV is imported, all debt records are created with status IMPORTED.
Once emails are successfully sent to customers, the status is automatically updated
to NOTIFIED.
Further status transitions (to Promised and Paid) are added in later sprints.
The backend enforces allowed transitions and stops invalid jumps.
This logic lives in the Debts service (\texttt{apps/api/src/services/debts.ts}).

\subsubsection{CSV Import and Campaign Creation}

The CSV import endpoint (\texttt{POST /api/v1/campaigns/actions/import}) uses a
tolerant, production-ready importer:

\begin{enumerate}
  \item Receives the file as multipart/form-data with campaign metadata (name, dueDate, optional description)
  \item Detects the delimiter (comma, semicolon, or tab) and parses CSV rows correctly
  \item Resolves header aliases using flexible matching (e.g., \texttt{fullName}, \texttt{full\_name}, \texttt{name} all map to the same column; \texttt{amount}, \texttt{montant}, \texttt{debt} map to amount)
  \item Validates required columns (full name, email, amount) and skips rows missing required fields
  \item Normalizes fields (email lowercasing, amount parsing) and deduplicates clients by email within the same CSV
  \item Executes a single database transaction (120-second timeout) to create/link clients and create debt records with initial status IMPORTED
  \item Returns a detailed import summary (total rows, imported, skipped with skip reasons)
  \item After transaction commit, immediately triggers asynchronous email sending to all customers
\end{enumerate}

All rows that fail to parse are returned to the user with detailed error messages, allowing managers to correct and re-import as needed.

\subsubsection{Workspace Isolation and Tenant Scope}

Each \texttt{Campaign} is tenant-scoped: it stores a \texttt{workspaceId} that ties the campaign and all its debts to a single workspace. All API endpoints, middleware and database queries enforce this constraint so that managers and agents only see resources belonging to their workspace. During CSV import, created client and debt records are associated with the campaign's \texttt{workspaceId}, ensuring no cross-tenant data leakage. This tenant-aware design simplifies RBAC checks, auditing, and campaign-level aggregation queries.


\subsubsection{Automatic Email Sending}

After a successful CSV import, the system automatically sends notification emails to all customers via the Brevo Transactional Email API:

\begin{itemize}
  \item \textbf{Email Subject:} \texttt{Collectra | New debt notice for \{campaign name\}}
  \item \textbf{Email Format:} HTML with customer greeting, campaign name, debt amount (formatted as currency), due date, and a prominent red call-to-action button
  \item \textbf{Button Text:} ``Open secure debt page''
  \item \textbf{Button Link:} Points to \texttt{\{publicDomain\}/client/view?token=\{jwt\}}
  \item \textbf{Concurrency:} Emails sent concurrently (up to 8 at a time) to minimize delivery delay
  \item \textbf{Tracking:} Email open events tracked via Brevo's tracking pixel; click events logged when customer visits the secure link
  \item \textbf{Metadata:} Email tagged with campaign and debt IDs for server-side filtering and analytics
  \item \textbf{Audit Trail:} System records EMAIL\_SENT action in CustomerActionHistory and logs event in BrevoEventLog
  \item \textbf{Status Update:} After emails sent, debt status automatically updates from IMPORTED to NOTIFIED
\end{itemize}

If email generation or sending fails for a debt, the error is logged but does not block the campaign creation or other customer emails.

\subsubsection{JWT Customer Links}

Personal links are signed JSON Web Tokens (HMAC-SHA256).
The token encodes the debt ID in the \texttt{sub} claim and is signed using the
server secret with algorithm HS256.
Tokens have a default expiry of 30 days (see \texttt{EXPIRY\_DAYS} in
\texttt{apps/api/src/lib/customer-jwt.ts}).
Token verification is stateless (no database row lookup required) and is done by
\texttt{verifyCustomerToken} when the public link is opened.

When a customer clicks the link in their email, the system:

\begin{enumerate}
  \item Verifies the JWT signature and expiry
  \item Retrieves and displays the debt details (customer name, campaign name, amount, due date, current status)
  \item Records a LINK\_CLICKED action in the audit history for manager reporting
  \item Logs the click event for campaign tracking analytics
\end{enumerate}

Customer actions (link click, page view) are recorded in \texttt{CustomerActionHistory} and Brevo event logs for later manager analytics.

member roles -- are protected by a role guard middleware.
The guard reads the requesting user's workspace role from the database and rejects
the request with \texttt{403 Forbidden} if the role is not sufficient.
Agents who try Manager-only operations receive a clear error with no data leak.

\subsection{Sprint 4 Business Logic}

\subsubsection{Payment Confirmation and Idempotency}

The payment pipeline was hardened to stop duplicate charges and stale frontend
states.
After the Stripe redirect, the client calls a verification endpoint and polls until
the database confirms the debt as \textit{Paid}.
Server-side confirmation is idempotent: repeated webhook or verification calls do
not cause duplicate state transitions.

The backend applies the following safeguards:
\begin{itemize}
  \item a \texttt{pendingStripeSessionId} lock to block concurrent checkout
        sessions;
  \item strict eligibility checks before payment starts (status and promise-date
        rules);
  \item idempotent confirmation that updates debt status only once.
\end{itemize}

This stops duplicate payment initiation and keeps the UI state aligned with the
backend data.

\subsubsection{Invoice Generation and Delivery}

Invoice generation happens only after confirmed payment.
When the debt moves to \textit{Paid}, the service creates or reuses a stable
invoice number, exposes a secure public invoice endpoint, and redirects users to
the hosted invoice or printable PDF.

The invoice email is sent as a side effect through Brevo after payment confirmation,
so that payment state remains the primary source of truth even if email delivery
fails.

\subsubsection{Email Tracking and Manager Analytics}

Campaign import and communication flows now save normalized tracking actions
(\textit{Email Sent}, \textit{Link Clicked}, and mapped provider events) into
the action history.
Manager endpoints group these events into operational metrics and refresh them in
near real time.

The final dashboard therefore combines:
\begin{itemize}
  \item debt lifecycle KPIs;
  \item payment and invoice completion visibility;
  \item communication performance metrics for campaign follow-up decisions.
\end{itemize}

  \item \textbf{Reliability:} Zod validates every API input at runtime, and the
        idempotent payment confirmation logic stops duplicate state transitions no
        matter how many times the verify endpoint is called.
  \item \textbf{Usability:} iterative sprint reviews with PeakSoft stakeholders
        confirmed that the workflow from campaign creation to payment confirmation
        needs only a small amount of training for new collection agents.
\end{itemize}

\textbf{Technical contributions.}
From a technical side, the project shows a full-stack TypeScript monorepo
architecture combining Next.js, Hono, Prisma, and Supabase in a production-grade
setup.
Using Zod for both runtime validation and OpenAPI schema generation, together with
workspace-level data isolation enforced at every layer, shows how security and
maintainability can be built in from the very start of a project.
The final implementation also shows robust financial-flow design through
duplicate-session prevention, idempotent confirmation logic, and post-transaction
invoice and email side effects.

\textbf{Challenges encountered.}
The main challenges during the project were:
\begin{itemize}
  \item designing a flexible but strict debt status transition system that stops
        invalid lifecycle jumps while staying easy to extend;
  \item handling large CSV files efficiently without overloading the database or
        causing request timeouts;
  \item securing the Stripe payment return path to avoid duplicate charges while
        keeping customer feedback fast during webhook delays;
  \item applying correct workspace isolation at every layer of the application,
        from database queries to API middleware to frontend navigation.
\end{itemize}
Each challenge was solved through careful schema design, server-side validation,
and iterative testing with real data.

\textbf{Personal learning outcomes.}
This internship gave me hands-on experience in full-stack TypeScript development,
agile project management with Scrum, and professional software delivery in a real
company environment.
It deepened my understanding of authentication flows, role-based access control,
JWT-based security, real-world relational data modeling, and production deployment
with Vercel and GitHub CI/CD pipelines.

\textbf{Perspectives and future work.}
Several improvements could extend the Collectra platform in the future:
\begin{itemize}
  \item integration with SMS or WhatsApp for direct, automated customer
        notifications;
  \item a scheduled background job for automatic overdue debt detection;
  \item campaign report export in PDF or Excel format;
  \item a mobile-responsive redesign or dedicated mobile application;
  \item advanced analytics and collection performance reporting for managers.
\end{itemize}

In conclusion, Collectra meets all the objectives set at the start of the
internship.
It gives collection teams a secure, structured, and easy-to-use platform that
replaces scattered tools with one purpose-built solution for debt management.

\chapter{Database Schema}
\label{app:schema}

Figure~\ref{fig:db-schema} shows the Entity-Relationship diagram for the Collectra
database.

\diagram[fig:db-schema]{Digrams/database.png}%
  {Collectra Database Schema -- Entity-Relationship Diagram}

The main tables and their roles are:
\begin{itemize}
  \item \texttt{User} -- authenticated user accounts managed through Supabase Auth;
  \item \texttt{Workspace} -- isolated tenant environments, each with its own data;
  \item \texttt{WorkspaceMember} -- links users to workspaces with an assigned role;
  \item \texttt{Invitation} -- pending or accepted membership invitations;
  \item \texttt{Campaign} -- debt collection campaigns scoped to a workspace;
  \item \texttt{Debt} -- individual debt records linked to a campaign and debtor;
  \item \texttt{PaymentPromise} -- recorded payment commitment dates for debts;
  \item \texttt{CustomerActionHistory} -- timeline of operations (status updates,
        promises, payments, tracking events);
  \item \texttt{BrevoEventLog} -- provider-level email event logs used for
        diagnostics and synchronization.
\end{itemize}
